```text
===============================================================================
FILE: arch/x86_64/kernel/sys_x86_64.c
PURPOSE: x86-64 SPECIFIC SYSTEM CALL HELPERS
KERNEL: Linux 2.6.x
===============================================================================

BACKGROUND
===============================================================================

Most Linux syscalls are architecture-independent.

Example:

    read()
    write()
    open()
    close()

Generic kernel code can implement these.

But some syscalls need architecture-specific behavior because:

    calling conventions differ
    virtual address layout differs
    compatibility mode exists
    user/kernel ABI differs
    32-bit emulation needs special handling

This file contains small x86-64-specific syscall wrappers and helpers.

It implements:

    sys_pipe()
    sys_mmap()
    arch_get_unmapped_area()
    sys_uname()

===============================================================================
BIG PICTURE
===============================================================================

Userspace syscall
        |
        v
x86-64 syscall entry
        |
        v
sys_x86_64.c helper
        |
        v
generic kernel implementation

Example:

    pipe()
        |
        v
    sys_pipe()
        |
        v
    do_pipe()

===============================================================================
WHY THIS FILE IS SMALL
===============================================================================

This file is not the main syscall implementation.

It is mostly glue between:

    x86-64 ABI

and

    generic kernel functions

For example:

    sys_pipe()

does not implement pipes.

It calls:

    do_pipe()

===============================================================================
PART 1: sys_pipe()
===============================================================================

Function:

    asmlinkage long sys_pipe(int __user *fildes)

Purpose:

    create a pipe and return two file descriptors to userspace.

Userspace:

    int fd[2];

    pipe(fd);

After success:

    fd[0] = read end
    fd[1] = write end

===============================================================================
WHY sys_pipe() IS SPECIAL
===============================================================================

On some old Unix ABIs, pipe returned two file descriptors in registers.

But the normal C API expects:

    pipe(int fd[2])

So x86-64 syscall wrapper creates:

    int fd[2]

in kernel stack, then copies them to userspace.

===============================================================================
sys_pipe() FLOW
===============================================================================

sys_pipe(fildes)
    |
    v
do_pipe(fd)
    |
    +--> create pipe inode
    +--> allocate two file objects
    +--> allocate two file descriptors
    |
    v
copy_to_user(fildes, fd, 2*sizeof(int))
    |
    v
return 0 or error

===============================================================================
IMPORTANT SECURITY POINT
===============================================================================

The kernel cannot directly trust:

    fildes

because it is a userspace pointer.

So it uses:

    copy_to_user()

If userspace pointer is invalid:

    return -EFAULT

===============================================================================
PART 2: sys_mmap()
===============================================================================

Function:

    sys_mmap(addr, len, prot, flags, fd, off)

Purpose:

    implement mmap syscall wrapper for x86-64.

It validates arguments, gets file object if needed, and calls:

    do_mmap_pgoff()

===============================================================================
MMAP BACKGROUND
===============================================================================

mmap creates a virtual memory mapping.

Examples:

    map file into memory

    allocate anonymous memory

    map shared memory

    create executable mappings

Userspace:

    mmap(NULL, 4096, PROT_READ|PROT_WRITE,
         MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);

Kernel creates:

    vm_area_struct

inside current->mm.

===============================================================================
sys_mmap() FLOW
===============================================================================

sys_mmap()
    |
    +--> validate file offset alignment
    |
    +--> clear MAP_EXECUTABLE / MAP_DENYWRITE
    |
    +--> if file-backed:
    |       fget(fd)
    |
    +--> down_write(&current->mm->mmap_sem)
    |
    +--> do_mmap_pgoff()
    |
    +--> up_write(&current->mm->mmap_sem)
    |
    +--> fput(file)
    |
    v
return mapped address or error

===============================================================================
OFFSET ALIGNMENT
===============================================================================

Code:

    if (off & ~PAGE_MASK)
        return -EINVAL

Meaning:

    mmap offset must be page-aligned.

Why?

Page tables map pages.

File offset must start at page boundary.

===============================================================================
MAP_ANONYMOUS CASE
===============================================================================

If:

    flags & MAP_ANONYMOUS

then:

    no file is needed.

Example:

    malloc large allocation

    thread stack

    anonymous private memory

===============================================================================
FILE-BACKED CASE
===============================================================================

If not MAP_ANONYMOUS:

    file = fget(fd)

This converts file descriptor into:

    struct file *

Reference count is incremented.

After mmap setup:

    fput(file)

drops reference.

===============================================================================
mmap_sem
===============================================================================

current->mm->mmap_sem protects the process VMA tree/list.

mmap modifies address space.

Therefore:

    down_write()

is required.

===============================================================================
PART 3: find_start_end()
===============================================================================

Function:

    find_start_end(flags, &begin, &end)

Purpose:

    choose address search range for mmap placement.

Normal 64-bit process:

    begin = TASK_UNMAPPED_BASE
    end   = TASK_SIZE

Special case:

    MAP_32BIT

===============================================================================
MAP_32BIT BACKGROUND
===============================================================================

MAP_32BIT asks kernel to place mapping in low 2GB-ish address range.

On x86-64 this was useful for:

    old code models

    thread stacks

    performance assumptions on early AMD64

This code uses:

    begin = 0x40000000
    end   = 0x80000000

So mappings are searched in:

    1GB to 2GB range

===============================================================================
WHY ONLY NON-IA32?
===============================================================================

Condition:

    !TIF_IA32 && MAP_32BIT

Meaning:

    only native 64-bit tasks using MAP_32BIT get this special range.

32-bit compatibility tasks already have their own 32-bit layout.

===============================================================================
PART 4: arch_get_unmapped_area()
===============================================================================

This is the most important function in the file.

Purpose:

    find a free virtual address range for mmap.

Called when user passes:

    addr = NULL

or when requested address cannot be used.

===============================================================================
VMA BACKGROUND
===============================================================================

A process address space is made of VMAs:

    [ text ]
    [ heap ]
    [ mmap region ]
    [ stack ]

Each VMA is:

    struct vm_area_struct

with:

    vm_start
    vm_end

arch_get_unmapped_area() finds a hole between VMAs.

===============================================================================
ADDRESS SPACE EXAMPLE
===============================================================================

Process virtual memory:

0x400000      text
0x600000      data
0x10000000    heap
0x40000000    free hole
0x50000000    mmap mapping
0x7fff0000    stack

Kernel needs to find:

    free hole of length len

===============================================================================
arch_get_unmapped_area() FLOW
===============================================================================

1. Select begin/end range.

2. If user provided addr:
       check if addr is free.
       if free, return it.

3. Start from mm->free_area_cache.

4. Walk VMA list using find_vma().

5. Find first hole large enough.

6. Update mm->free_area_cache.

7. Return address.

===============================================================================
USER-SUPPLIED ADDRESS CASE
===============================================================================

If user passes addr:

    addr = PAGE_ALIGN(addr)

Kernel checks:

    no VMA overlaps [addr, addr+len)

If valid:

    return addr

This is only a placement hint unless MAP_FIXED is handled elsewhere.

===============================================================================
free_area_cache
===============================================================================

mm->free_area_cache remembers where last mmap search ended.

Why?

Most mmap calls happen repeatedly.

Instead of searching from beginning each time:

    start from cached address

Improves performance.

===============================================================================
cached_hole_size
===============================================================================

mm->cached_hole_size remembers largest hole recently skipped.

If requested len is small enough, search may restart efficiently.

Special logic resets cache for:

    MAP_32BIT

    IA32 tasks

because address range differs.

===============================================================================
FULL SEARCH LOOP
===============================================================================

Pseudo-code:

    for each VMA after addr:

        if addr + len fits before vma->vm_start:
            return addr

        else:
            addr = vma->vm_end

If end reached:

    return -ENOMEM

===============================================================================
WHY RETURN -ENOMEM?
===============================================================================

Not because physical memory is exhausted.

Because virtual address space has no free hole large enough.

===============================================================================
PART 5: sys_uname()
===============================================================================

Function:

    sys_uname(struct new_utsname __user *name)

Purpose:

    copy kernel system identity to userspace.

Userspace:

    uname -a

or:

    uname(&uts)

Kernel fills:

    sysname
    nodename
    release
    version
    machine
    domainname

===============================================================================
sys_uname() FLOW
===============================================================================

sys_uname()
    |
    v
down_read(&uts_sem)
    |
    v
copy_to_user(name, utsname(), sizeof(*name))
    |
    v
up_read(&uts_sem)
    |
    v
if PER_LINUX32:
        overwrite machine with "i686"

===============================================================================
WHY uts_sem?
===============================================================================

UTS namespace data can change.

Example:

    sethostname()

So reading it requires synchronization.

===============================================================================
WHY RETURN "i686" FOR LINUX32?
===============================================================================

A 32-bit compatibility process may expect:

    machine = i686

not:

    x86_64

So if personality is:

    PER_LINUX32

kernel lies for compatibility.

This helps old 32-bit programs behave correctly.

===============================================================================
COMPATIBILITY PERSONALITY
===============================================================================

personality controls ABI quirks.

Examples:

    PER_LINUX

    PER_LINUX32

For 32-bit emulation on x86-64:

    PER_LINUX32

makes some syscalls report 32-bit-like behavior.

===============================================================================

    generic mmap implementation

===============================================================================
MENTAL MODEL
===============================================================================

This file is not a big subsystem.

It is architecture glue.

It adapts generic Linux functionality to x86-64 ABI details:

    pipe fd return convention

    mmap offset/page rules

    64-bit vs 32-bit address layout

    low-address MAP_32BIT placement

    uname compatibility behavior

===============================================================================
ONE SENTENCE SUMMARY
===============================================================================

arch/x86_64/kernel/sys_x86_64.c provides small but important x86-64
syscall glue routines: it implements pipe() by returning descriptors
through a userspace array, wraps mmap() around do_mmap_pgoff() with
x86-64 validation and address-space locking, chooses architecture-specific
unmapped virtual address ranges including MAP_32BIT handling, and adjusts
uname() results for 32-bit compatibility personalities.
===============================================================================
```
